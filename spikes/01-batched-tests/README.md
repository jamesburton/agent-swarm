> THROWAWAY SPIKE — batched integration tests + bisect. Run 2026-10-02 on a shared, ~100%-CPU machine (wall times pessimistic; compare run counts).

**Question:** how much does batching + bisect save over one full suite per task, and which variant is better?

Sandbox: generated by `../shared/sandbox-gen.cs` (6 projects x 10 tests, 12 tasks; `--failing 1|2` seeds two-task interaction failures). Run: `dotnet run simulate.cs` in `a/` or `b/`.

| Full-suite runs (12 tasks) | Serial | A: fixed N=4 + halving | B: adaptive 2-8 + overlap pre-batch + halving |
|---|---|---|---|
| failing 0 | 12 | 3 | 3 |
| failing 1 | 12 | 6 | 7 |
| failing 2 | 12 | 7 | 8 |
| Culprits correct | n/a | yes (T002; T002+T004) | yes (same) |
| Crashed-lock reclaim | n/a | 4.8 s (10 s expiry demo) | 2.6 s (6 s expiry demo) |
| Squash at green, trailers | n/a | yes, tree matches tested tree | yes |

Caveats (both): serial is modelled, not run; stop-on-conflict coded but never exercised (sandbox merges cleanly); bisect infers the right half red after a green left half (skips a run); the blamed task is the later one of an interacting pair. B's overlap data is synthesized. Modelled seconds use different per-run times (A 237 s, B 142.8 s), so not comparable.

**Verdict:** batching works: 2-4x fewer full runs. A beat B on this workload (adaptive sizing and pre-batching bought nothing when tasks never overlap and failures are pair interactions). Open: pre-batching likely matters with real overlapping edits; test with a conflict-prone sandbox.
